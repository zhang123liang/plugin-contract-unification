# 插件契约统一化

> 一个契约统一所有能力。不要再为每个工具单独写适配器。

## 问题

函数、类、API、工具和智能体通常形态不同。它们有不同的调用方式、生命周期、错误风格和配置格式。

项目变大后，这些东西会变成大量胶水代码：

- 工具要单独加载
- API 要单独包装
- 模型要单独适配
- 服务要单独处理

每增加一种能力，就多一个集成问题。

## 原子思路

把所有能力统一包装成同一个契约：

```text
name + schema + lifecycle + handler
```

`handler` 是能力背后的具体执行逻辑。

然后一个注册中心就可以用同一种方式加载、调用、替换和卸载它们。这样就能把异构能力变成可替换插件，而不用反复重写外围系统。

## 开发者为什么关注

- 减少自定义适配器。
- 支持热替换能力。
- 统一 Schema 和错误码。
- 生命周期清晰：注册、加载、运行、替换、卸载。
- 有一致性测试验证契约可运行。
- 参考实现小而零依赖。

改造前：

```text
每个工具、API、模型、服务各写一个适配器
```

改造后：

```text
registry.register(plugin)
```

## 快速开始

运行参考实现自测：

```bash
python -B skill.py
```

运行一致性测试：

```bash
python -B conformance.py
```

## 前景

目标是把这个插件契约做成一个轻量、中立的集成标准：

```text
能力 + 契约 + 注册中心 = 可替换系统
```

它不应该要求开发者引入整套 Agent 框架。它应该小到可以直接放进现有项目，同时严格到让不同能力按同一方式运行。

## 路线图

当前：

- 语言无关契约
- 单文件参考实现
- 一致性测试套件

下一步：

- 更多常见集成模式示例
- CI 徽章和可复现的一致性测试结果
- 更多语言绑定
- 贡献与兼容性指南

后期：

- 支持超时、隔离和监控的生产运行时
- 托管注册中心和治理服务
- 基于同一契约的企业内部 / 行业专用插件系统

## 生产版方向

同一套契约可以用于建设：

- AI 编码助手技能系统
- 企业工具与 Agent 总线
- 企业内部 / 行业专用插件系统
- 带治理和审计的插件注册服务

生产版可以保持私有或单独授权。当前仓库只提供契约、参考实现和一致性测试。

## 非目标

- 不是一个完整的智能体框架。
- 不是生产版或旗舰产品。
- 不是某个具体框架的复刻。
- 不是任何上游项目的官方产品。
